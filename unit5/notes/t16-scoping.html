Scoping

Scope decides where a variable can be seen and changed: the whole session, one script, or one function.

Topic 16~20 min
Before this:06 Writing scripts08 Variables15 Functions
Key idea

A child scope can read its parent's variables. Assigning to one inside the child creates a new local copy; the parent's value stays the same.

Scopes are nested boxes

Global

The PowerShell session: your prompt and your profile.

Script

Created each time a .ps1 file runs. Gone when it ends.

Local (function)

Created each time a function runs. Gone when it returns.

ScopeWhat it isWritten as
GlobalThe whole session$global:x
ScriptThe running script file$script:x
LocalWherever the code is running now$x (default)
PrivateLike local, but child scopes cannot see it$private:x
NoteLocal is not a separate box. It just means "the current box". At the prompt, local is global.

A child can read the parent

powershell
$color = 'blue'
function Show-Color { "Inside: $color" }
Show-Color
output
Inside: blue

Assigning makes a local copy

powershell
$count = 1
function Add-One {
    $count = $count + 1      # new local $count
    "Inside: $count"
}
Add-One
"Outside: $count"
output
Inside: 2
Outside: 1
  • Read $count: finds parent's 1
  • Assign: makes local $count = 2
  • Function ends: local copy is gone

$script: and $global: modifiers

A scope modifier says exactly which box to change.

powershell
$count = 1
function Add-One {
    $script:count = $script:count + 1
}
Add-One
Add-One
"Count: $count"
output
Count: 3
powershell
function Set-Theme { $global:theme = 'dark' }
Set-Theme
$theme
output
dark

$private: hides a variable from child scopes.

powershell
$private:pin = 1234
function Show-Pin { "PIN: $pin" }
Show-Pin
output
PIN:
Watch outUse $global: rarely. Any script can change a global variable, which makes bugs hard to find.

Dot-sourcing changes scope

Running a script gives it its own script scope. Dot-sourcing (. then a space) runs it in your scope, so its variables and functions stay. Save this one-line file as setvars.ps1 in the unit5 folder:

setvars.ps1
$siteName = 'StudentPortal'
powershell
./setvars.ps1         # normal run: own scope
"After run: $siteName"
. ./setvars.ps1       # dot-source: your scope
"After dot-source: $siteName"
output
After run:
After dot-source: StudentPortal
CommandRuns inVariables after it ends
./setvars.ps1a new script scopegone
. ./setvars.ps1the current scopekept

This is how a profile or a library file adds functions to your session. See 19 Script files.

Best practice: parameters in, values out

Don't reach into other scopes. Pass values in as parameters and return the result.

powershell
function Add-One {
    param([int]$Value)
    $Value + 1
}
$count = 1
$count = Add-One $count
$count
output
2

Try it

  1. Set $name = 'Rohan'. Write a function that prints it. Does it work?
  2. Inside the function, set $name = 'Isha'. What is $name after the call?
  3. Change the function so the outside $name really becomes Isha.
Answers
powershell
$name = 'Rohan'
function Show-Name { $name }
Show-Name                              # Rohan (child reads parent)

function Set-Name { $name = 'Isha' }
Set-Name; $name                        # Rohan (only a local copy changed)

function Set-Name { $script:name = 'Isha' }
Set-Name; $name                        # Isha
# Better: function Get-NewName { 'Isha' }; $name = Get-NewName

Remember

  • Scopes nest: global → script → function.
  • Children can read parents; assigning makes a local copy.
  • $script:x and $global:x change a specific scope.
  • . ./file.ps1 runs a file in your scope.
  • Prefer parameters and return values over scope modifiers.
VivaWhat is dot-sourcing? Running a script with a dot and a space in front, . ./lib.ps1. The script runs in the caller's scope, so its variables and functions remain available after it finishes.

Lab 09: Pipes and redirection

Every command reads input and writes two kinds of output: normal results and error messages. This lab shows how to send that output into files (>, >>, 2>), into other commands (|), or both at once (tee).

Syntax: > >> < 2> 2>&1 | tee <<EOFDifficulty: beginner~45 min

Aim and objectives

Aim: control where a command's input comes from and where its output and errors go.

  • Save output in a file with > and add to a file with >>.
  • Separate error messages with 2>, or combine them with 2>&1.
  • Join commands with a pipe |.
  • Show and save output at the same time with tee.
  • Use a here-document, one process substitution and one exec redirection.

Prerequisites

Only Bash and the standard tools. Run every example from the project folder so that datasets/ is found. The examples create small files such as report.txt in the current folder.

Step 1: > and >>, save output in a file

bash · save_output.sh
#!/bin/bash
# save_output.sh: > writes a new file, >> adds to the end of a file
echo "Web log report" > report.txt                 # > creates report.txt (or empties it)
echo "Requests: $(grep -c '' datasets/access.log)" >> report.txt   # >> adds a line
echo "404s    : $(grep -c ' 404 ' datasets/access.log)" >> report.txt
cat report.txt                                     # show the file

echo "Second run" > report.txt                     # > again: old content is gone!
echo "--- after using > again:"
cat report.txt
bash · run it
chmod +x save_output.sh
./save_output.sh
output
Web log report
Requests: 80
404s    : 8
--- after using > again:
Second run
  • > file creates the file, or empties it first if it already exists.
  • >> file adds to the end and keeps what was there.
  • The last part shows the danger: a second > wiped the whole report.

Step 2: 2> and 2>&1, handle error messages

Here grep gets two files: missing.log does not exist (an error) and datasets/auth.log does (a result).

bash · errors.sh
#!/bin/bash
# errors.sh: stdout (1) and stderr (2) are separate streams
grep -c 'Failed' missing.log datasets/auth.log > out.txt 2> err.txt   # split them
echo "out.txt has: $(cat out.txt)"
echo "err.txt has: $(cat err.txt)"

grep -c 'Failed' missing.log datasets/auth.log > all.txt 2>&1         # both into one file
echo "all.txt has:"
cat all.txt

echo "errors hidden:"
grep -c 'Failed' missing.log datasets/auth.log 2> /dev/null           # throw errors away
output
out.txt has: datasets/auth.log:27
err.txt has: grep: missing.log: No such file or directory
all.txt has:
grep: missing.log: No such file or directory
datasets/auth.log:27
errors hidden:
datasets/auth.log:27
  • The number 1 is normal output (stdout), 2 is error output (stderr). > is short for 1>.
  • 2> err.txt sends only the errors to err.txt.
  • > all.txt 2>&1 means "stdout to all.txt, then stderr to the same place as stdout".
  • 2> /dev/null throws errors away. /dev/null is a special file that deletes everything written to it.

Step 3: |, a simple pipe

bash · pipe.sh
#!/bin/bash
# pipe.sh: | sends the output of one command into the next command
echo "Step 1, all status codes (first 5):"
awk '{print $9}' datasets/access.log | head -5        # column 9 = HTTP status

echo "Step 2, count each code, most common first:"
awk '{print $9}' datasets/access.log | sort | uniq -c | sort -rn
output
Step 1, all status codes (first 5):
200
200
200
200
301
Step 2, count each code, most common first:
     55 200
      9 403
      8 404
      6 500
      1 302
      1 301
  • A pipe connects the output of the left command to the input of the right command. No file is created.
  • Read the pipeline left to right: print column 9 → sort them → count repeats → sort by count, biggest first.
  • uniq -c only counts lines that are next to each other, which is why sort comes first.

Step 4: tee, show and save at the same time

bash · tee_demo.sh
#!/bin/bash
# tee_demo.sh: tee shows the output AND saves it in a file

Concepts

File descriptors 0, 1 and 2

Every command starts with three open "channels", numbered 0, 1 and 2. They are called file descriptors.

NumberNameDefaultUsed for
0stdinkeyboardinput the command reads
1stdoutscreennormal results
2stderrscreenerror messages

Redirection cheat sheet

SyntaxMeaning
cmd > filestdout to file (file is emptied first)
cmd >> filestdout added to the end of file
cmd < filestdin read from file
cmd 2> fileerrors to file
cmd > file 2>&1results and errors to the same file
cmd &> fileBash shortcut for the line above
cmd 2> /dev/nullhide errors
cmd1 | cmd2output of cmd1 becomes input of cmd2
cmd | tee fileshow on screen and save to file (-a to append)
echo "msg" >&2print a message to stderr (for error messages in scripts)

Order matters: > file 2>&1 vs 2>&1 > file

Bash reads redirections from left to right. 2>&1 means "send errors where stdout goes right now".

bash · try both orders
cat nope.txt > out.txt 2>&1      # stdout to file first, then errors follow: nothing on screen
cat out.txt
cat nope.txt 2>&1 > out.txt      # errors go to the screen (stdout's place at that moment)
output
cat: nope.txt: No such file or directory
cat: nope.txt: No such file or directory
VivaRemember: "first say where stdout goes, then send stderr to the same place": cmd > file 2>&1.

Here-documents and here-strings

A here-document gives several lines of input written inside the script, ending at a line that contains only the end word (often EOF).

bash · heredoc.sh
name="student"
cat <<EOF
Hello $name
2 + 3 = $((2 + 3))
EOF
cat <<'EOF'
Hello $name     (quotes around EOF: nothing is replaced)
EOF
output
Hello student
2 + 3 = 5
Hello $name     (quotes around EOF: nothing is replaced)

A here-string <<< gives one line of input:

bash · here-string
tr 'a-z' 'A-Z' <<< "hello world"
output
HELLO WORLD
Writing a file with a here-documentcat > notes.txt <<EOF … EOF creates notes.txt with those lines. Handy for creating config files from a script.

Did the pipe work? $? and PIPESTATUS

$? holds the exit status of the last command: 0 means success. For a pipeline, it is the status of the last command only. PIPESTATUS lists all of them.

bash · exit status of a pipe
cat nope.txt | sort
echo "Statuses: ${PIPESTATUS[*]}"     # cat failed (1), sort worked (0)
output
cat: nope.txt: No such file or directory
Statuses: 1 0

Use cases

Use case 1 Log report with a separate error log

What: a script counts the error responses in a web log. Results go into report.txt, problems (like a missing log file) go into errors.log. Why: the report stays clean, and you can still see what went wrong.

bash · errors_report.sh
#!/bin/bash
# errors_report.sh: count 4xx/5xx responses in a web log
# results go to stdout, problems go to stderr (so they can be saved separately)
log="$1"
if [ -z "$log" ]; then
  echo "Usage: $0 logfile" >&2                    # >&2 = print to stderr
  exit 1
fi
if [ ! -f "$log" ]; then
  echo "Error: $log not found" >&2
  exit 1
fi

echo "Error report for $log"
echo "Total requests: $(grep -c '' "$log")"
echo "Error responses by status:"
awk '$9 >= 400 {print $9}' "$log" | sort | uniq -c | sort -rn
bash · run it on a good file and a missing file
./errors_report.sh datasets/access.log > report.txt 2> errors.log
./errors_report.sh datasets/old.log >> report.txt 2>> errors.log
echo "exit status: $?"

How it works

  • echo "…" >&2 prints the message on stderr, so 2> errors.log catches it while report.txt only gets results.
  • exit 1 tells the caller the script failed; $? shows it.
  • The second run uses >> and 2>> so the earlier results are kept.
  • [ ! -f "$log" ] is true when the file does not exist.

Use case 2 A script that logs everything with exec

What: an HR summary job that writes all of its output, including errors from commands, into hr_summary.log. Why: when a job runs from cron nobody watches the screen; the log is the only record.

Optional: going further (log to file AND screen with exec + tee)

Use case 2 hides everything from the screen. To see the output and log it, send the script's output through tee:

bash · top of a script
#!/bin/bash
exec > >(tee -a job.log) 2>&1     # everything goes to tee: screen + job.log
echo "this line is on the screen and in job.log"
output
this line is on the screen and in job.log

>(tee -a job.log) is process substitution in the other direction: a "file" whose contents are fed to tee.

Viva / exam questions

What are file descriptors 0, 1 and 2?

0 is standard input (stdin), 1 is standard output (stdout) and 2 is standard error (stderr). By default 0 is the keyboard and 1 and 2 are the screen.

What is the difference between > and >>?

> empties the file and writes new content; >> adds to the end. Both create the file if it does not exist.

What does 2>&1 mean?

Send file descriptor 2 (errors) to the same place as file descriptor 1 (normal output). In cmd > file 2>&1 both end up in the file.

Why is cmd 2>&1 > file different from cmd > file 2>&1?

Redirections are applied left to right. In the first, errors are sent to where stdout points at that moment (the screen), and only then is stdout moved to the file, so errors stay on screen.

What is /dev/null?

A special file that discards everything written to it. 2> /dev/null hides error messages.

What is a pipe?

cmd1 | cmd2 connects the stdout of cmd1 to the stdin of cmd2, so the output of one command becomes the input of the next, without a temporary file.

What does tee do?

It copies its input to the screen and to a file at the same time. tee -a appends to the file instead of overwriting it.

What is a here-document?

A way to give several lines of input inside a script: cat <<EOF, the lines, then EOF on its own line. With <<'EOF' variables are not replaced.

What is process substitution?

<(command) runs the command and gives its output as a file name, so commands like diff that need files can compare command outputs: diff <(sort a) <(sort b).

grep: search text with patterns

grep prints the lines of its input that match a pattern. It is the fastest way to answer "where does this appear?", "how many times?" and "which files?", and with -o it becomes an extraction tool for IP addresses, e-mails and status codes. This page goes from plain-word searches to regular expressions, context lines, recursive search and using grep -q inside scripts.

Syntax and how it works

syntax
grep [OPTIONS] PATTERN [FILE...]
grep [OPTIONS] -e PATTERN1 -e PATTERN2 [FILE...]
grep [OPTIONS] -f PATTERNS_FILE [FILE...]
command | grep [OPTIONS] PATTERN          # read from standard input

Mental model: grep reads its input one line at a time, tests the line against the pattern, and prints the line if it matches. That is all. Every option only changes one of three things:

  1. How the pattern is interpreted: basic regex (default, -G), extended regex (-E), Perl regex (-P), or a fixed string (-F); case-insensitive (-i); whole word (-w) or whole line (-x).
  2. Which lines count as a "hit": normally matching lines; with -v the non-matching ones.
  3. What is printed: the line (default), only the matched part (-o), a count (-c), file names (-l/-L), nothing at all (-q), plus decorations like line numbers (-n) and context (-A/-B/-C).

Exit status: grep as a test

grep's exit code is what makes it useful in if statements:

Exit codeMeaningTypical use
0at least one line matchedif grep -q ... ; then
1no line matched"not found" branch
2error (missing file, bad regex)should abort the script
bash
grep -q 'Accepted publickey' datasets/auth.log; echo "exit=$?"
grep -q 'Accepted password'  datasets/auth.log; echo "exit=$?"
grep -q 'x' datasets/no-such-file.log;          echo "exit=$?"
output
exit=0
exit=1
grep: datasets/no-such-file.log: No such file or directory
exit=2
Viva"What does grep return when nothing matches?", exit status 1, not an error. Only status 2 is an error. This matters with set -e: a grep that finds nothing will stop your script unless you write grep ... || true.

Regular expressions: BRE vs ERE vs PCRE

grep understands three regex dialects. They share the same core (., *, [...], ^, $) and differ mainly in which characters need a backslash.

FeatureBRE, grepERE, grep -EPCRE, grep -P
one or morea\+ (GNU extension)a+a+
zero or onea\? (GNU extension)a?a?
alternationcat\|dog (GNU extension)cat|dogcat|dog
grouping\(ab\)*(ab)*(ab)*, (?:ab)
intervala\{2,3\}a{2,3}a{2,3}
back-reference\(a\)\1(a)\1(a)\1
digit[0-9], [[:digit:]][0-9], [[:digit:]]\d
lookahead / lookbehind--(?=...), (?<=...)
lazy quantifier--.*?
literal + ? | ( ) { }written plainneeds backslashneeds backslash

Rule of thumb: use grep -E for anything beyond a plain word. Use -P only when you need \d, lookarounds or lazy matching, and only on Linux (GNU grep). Use -F when the "pattern" is really a literal string full of dots and brackets (IP addresses, file paths, version numbers).

-w: whole words only

The letters on appear inside other words (configuration, FEATURE_EMAIL=on). Compare:

bash

grep -w 'on' datasets/app.conf
output
2
FEATURE_EMAIL=on

A "word" is a run of letters, digits and underscores. -w requires that the match is not preceded or followed by such a character:

bash
grep -c -w 'APP' datasets/app.conf
grep -c 'APP' datasets/app.conf
output
0
4

APP occurs four times as a prefix (APP_NAME …), but never as a whole word, because _ counts as a word character.

Back-references

A back-reference \1 matches the same text that group 1 matched. Classic uses are finding repeated words (a common typo) or repeated characters:

bash
printf 'the the cat\nno repeat here\nis is it\n' | grep -E '\b([a-z]+) \1\b'
output
the the cat
is is it
bash
grep -oE '([0-9])\1\1' datasets/access.log | sort | uniq -c    # triple digits like 000, 111
output
      1 111
      1 222

-P: Perl regex (GNU grep)

PCRE adds shorthand classes (\d), non-greedy quantifiers and lookarounds, assertions that check context without including it in the match. With -o this lets you print just the value you want:

bash
grep -oP '(?<=for )\w+(?= from)' datasets/auth.log | sort | uniq -c | sort -rn
output
      7 sysadmin
      5 root
      4 deploy
      3 ubuntu
      3 test
      2 admin
      1 guest

(?<=for ) means "preceded by for ", (?= from) means "followed by from". Only the user name is printed. Another one, the value of a config key, without the key:

bash
grep -oP '^DB_\w+=\K.*' datasets/app.conf
output
localhost
3306
inventory
root
changeme

\K "keeps" only what comes after it. Response sizes larger than 50 000 bytes using \d:

bash
grep -oP '" 200 \K\d{5,}' datasets/access.log | sort -n | tail -3
output
51270
51436
51563
macOSThe BSD grep shipped with macOS has no -P. Install GNU grep (brew install grep, then use ggrep) or rewrite the expression with sed -E/awk. In exams on Linux, grep -oP is fine.

Use cases

Use case 1 Hunting failed SSH logins

Scenario: your server's /var/log/auth.log is full of Failed password lines. You need a quick report: total failures, failures for invalid (non-existent) users vs real users, the attacking IPs, the most-tried user names, and whether any attacking IP ever logged in successfully. Everything below is grep with a little sort/uniq.

bash · ssh_report.sh
#!/usr/bin/env bash
# ssh_report.sh - summarise failed SSH logins from an auth log
set -euo pipefail

log="${1:-/var/log/auth.log}"
threshold="${2:-5}"          # flag IPs with at least this many failures

if [[ ! -r "$log" ]]; then
  echo "error: cannot read $log" >&2
  exit 2
fi

ip_re='([0-9]{1,3}\.){3}[0-9]{1,3}'

total=$(grep -c 'Failed password' "$log" || true)
invalid=$(grep -c 'Failed password for invalid user' "$log" || true)
echo "== SSH failed-login report for $log =="
echo "Total failures      : $total"
echo "  invalid users     : $invalid"
echo "  existing accounts : $(( total - invalid ))"
echo

echo "-- Failures per source IP --"
grep 'Failed password' "$log" | grep -oE "from $ip_re" | cut -d' ' -f2 \
  | sort | uniq -c | sort -rn

echo
echo "-- Most targeted user names --"
grep -oE 'Failed password for (invalid user )?[a-z]+' "$log" \
  | awk '{print $NF}' | sort | uniq -c | sort -rn | head -5

echo
echo "-- IPs at or above threshold ($threshold) --"
grep 'Failed password' "$log" | grep -oE "$ip_re" | sort | uniq -c \
  | while read -r count ip; do
      if (( count >= threshold )); then
        # did this attacker EVER get in?
        if grep -q "Accepted .* from $ip " "$log"; then
          echo "  $ip ($count failures) - ALSO HAS A SUCCESSFUL LOGIN!"
        else
          echo "  $ip ($count failures) - candidate for blocking"
        fi
      fi
    done
bash · run it
./ssh_report.sh datasets/auth.log 5
output
== SSH failed-login report for datasets/auth.log ==
Total failures      : 27
  invalid users     : 13
  existing accounts : 14

-- Failures per source IP --
     12 45.33.32.156
      7 103.21.244.9
      5 91.240.118.172
      3 185.220.101.3

-- Most targeted user names --
      8 ubuntu
      7 root
      6 test
      4 admin
      2 guest

-- IPs at or above threshold (5) --
  103.21.244.9 (7 failures) - candidate for blocking
  45.33.32.156 (12 failures) - candidate for blocking
  91.240.118.172 (5 failures) - candidate for blocking

How it works:

  • grep -c ... || true: -c prints 0 but exits 1 when nothing matches; || true keeps set -e from killing the script.
  • grep -oE "from $ip_re": anchoring the IP on the word from guarantees we never extract a port or PID by mistake. The regex is kept in a variable so it is written once.
  • (invalid user )?: an optional group, so both "for root" and "for invalid user root" yield the user name as the last word.
  • grep -q "Accepted .* from $ip ": a silent test per IP; the trailing space stops 10.0.0.5 from also matching 10.0.0.55.
Going furtherFeed the "candidate for blocking" IPs into sudo ufw deny from IP or fail2ban. On systemd systems without auth.log use journalctl -u ssh --since today | grep 'Failed password'.

Step 3, the secret scan. Case-insensitive, extended regex, recursive, skipping node_modules, and showing only the matching part so long lines do not flood the screen:

bash · scan_secrets.sh
#!/usr/bin/env bash
# scan_secrets.sh - fail (exit 1) if likely secrets are hard-coded under DIR
set -uo pipefail
dir="${1:-.}"

pattern='(pass(word)?|secret|api_?key|token)[[:space:]]*[=:][[:space:]]*["'"'"']?[A-Za-z0-9_]{6,}|-----BEGIN [A-Z ]*PRIVATE KEY-----'

hits=$(grep -rniE --exclude-dir=node_modules --exclude-dir=.git \
            --include='*.env' --include='*.py' --include='*.sh' --include='*.conf' \
            "$pattern" "$dir" | sort)

if [[ -n "$hits" ]]; then
  echo "Possible secrets found:"
  printf '%s\n' "$hits"
  exit 1
fi
echo "No secrets found."
bash · run it
./scan_secrets.sh proj; echo "exit=$?"
output
Possible secrets found:
proj/config/prod.env:3:DB_PASS=changeme
proj/src/app.py:3:api_key = "EXAMPLE_KEY_123"
exit=1

Why these results?

  • prod.env:3 has a literal password value, a real finding.
  • app.py:3 has a hard-coded API key, a real finding. app.py:2 is not reported: after = the regex needs at least six word characters in a row ([A-Za-z0-9_]{6,}), but os is followed by a dot, so the run is only two characters long.
  • dev.env only mentions DB_PASS in a comment with no =, and deploy.sh reads $CF_API_TOKEN from the environment, both correctly ignored.
  • node_modules is skipped by --exclude-dir.

Because the script exits 1 on findings, it can be used as a Git pre-commit hook: ./scan_secrets.sh . || { echo "commit blocked"; exit 1; }.

Use case 3 Validating input formats with grep -qE

Scenario: a provisioning script takes a user name, an e-mail, an IPv4 address and a port from the user. Validate each one before using it. grep -qE with ^...$ anchors is the standard trick: the whole string must match, and grep's exit status drives the if.

bash · validate.sh
#!/usr/bin/env bash
# validate.sh - validate values with anchored extended regexes
set -uo pipefail

# matches VALUE against REGEX; returns grep's exit status
matches() {
  local value="$1" regex="$2"
  printf '%s\n' "$value" | grep -qE "$regex"
}

valid_username() { matches "$1" '^[a-z_][a-z0-9_-]{2,15}$'; }
valid_email()    { matches "$1" '^[[:alnum:]._%+-]+@[[:alnum:].-]+\.[[:alpha:]]{2,}$'; }
valid_port()     { matches "$1" '^[0-9]{1,5}$' && (( 10#$1 >= 1 && 10#$1 <= 65535 )); }
valid_ipv4() {
  local octet='(25[0-5]|2[0-4][0-9]|1[0-9]{2}|[1-9]?[0-9])'
  matches "$1" "^($octet\.){3}$octet\$"
}

check() {
  local kind="$1" value="$2"
  if "valid_$kind" "$value"; then
    printf '  %-9s %-28s OK\n' "$kind" "$value"
  else
    printf '  %-9s %-28s INVALID\n' "$kind" "$value"
  fi
}

check username deploy
check username 9lives
check email    priya.sharma@example.com
check email    priya@localhost
check ipv4     192.168.1.10
check ipv4     256.1.1.1
check ipv4     10.0.0
check port     8080
check port     70000
bash · run it

  username  9lives                       INVALID
  email     priya.sharma@example.com     OK

  ipv4      10.0.0                       INVALID
  port      8080                         OK
  port      70000                        INVALID

Key points:

  • Anchors are essential. Without ^ and $, [0-9]{1,5} would accept abc123xyz because part of it matches.
  • printf '%s\n' "$value" instead of echo: echo misbehaves with values like -n or -e.
  • The strict IPv4 regex builds an octet alternation (250–255 | 200–249 | 100–199 | 0–99) and repeats it, this is where regex groups pay off. It correctly rejects 256.1.1.1.
  • The port check combines a regex (digits only) with arithmetic (range), because regexes are bad at numeric ranges. 10#$1 forces base 10 so 08080 is not read as octal.
  • In Bash alone you could write [[ $v =~ regex ]]; using grep keeps the same regex portable to sh scripts and makes the dialect (ERE) explicit.

Viva / exam questions

What is the difference between grep, grep -E and grep -F?

Plain grep uses basic regex (BRE), where + ? | ( ) { } must be backslashed to be special. -E uses extended regex where they are special without a backslash. -F treats the pattern as a literal string with no special characters at all.

How do you count lines that do NOT contain a word?

grep -vc word file: -v inverts, -c counts.

What does grep -o do and why is it useful?

It prints only the matched part of each line, one match per line. Combined with sort | uniq -c it builds frequency tables (IPs, status codes, user names).

Difference between -l and -L?

-l lists files that contain at least one match; -L lists files that contain none.

How would you search only .php files recursively?

grep -r --include='*.php' PATTERN dir/

What does ^$ match?

An empty line, start of line immediately followed by end of line. grep -v '^$' removes blank lines.

Why use grep -q in a script?

It prints nothing and stops at the first match; only the exit status is used, which is exactly what an if needs.

What is a back-reference?

\1 refers to the exact text matched by the first parenthesised group. grep -E '(.)\1' finds any doubled character.
